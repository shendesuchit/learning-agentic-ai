> **Module:** LangChain Fundamentals
>
> **Level:** Beginner Software Engineers
>
> **Objective:** Learn how to control the behavior of Large Language Models using configuration parameters such as Temperature, Max Tokens, and Stop Sequences. These parameters determine **how** a model generates responses without changing the model itself.

---

# The Engineering Problem

Imagine you've successfully integrated GPT-4.1 into your application using LangChain.

Everything works perfectly.

Now your Product Manager comes to you with three new requirements.

### Application 1

> "Build an AI storyteller for children."

---

### Application 2

> "Build an AI legal assistant that reviews contracts."

---

### Application 3

> "Build an AI coding assistant."

Interestingly...

All three applications use the **same Large Language Model**.

The same GPT model.

The same API.

The same LangChain framework.

So should all three applications produce responses in exactly the same way?

Obviously not.

A storytelling application should generate imaginative, colorful, and varied responses.

A legal assistant should produce precise, consistent, and factual answers.

A coding assistant should generate deterministic code with minimal randomness.

This raises an important engineering question:

> **How can the same model behave differently without retraining it?**

The answer lies in **Model Configuration Parameters**.

These parameters allow developers to adjust how the model generates text during inference.

Think of them as runtime settings that influence the model's behavior.

---

# Understanding the Difference

Before discussing the parameters themselves, it's important to distinguish three concepts that beginners often confuse.

| Concept                      | Purpose                                                        |
| ---------------------------- | -------------------------------------------------------------- |
| **Model**                    | The intelligence (GPT, Claude, Gemini, Llama, etc.)            |
| **Prompt**                   | Instructions given to the model                                |
| **Configuration Parameters** | Runtime settings controlling how the model generates responses |

Changing one does not necessarily change the others.

---

# A Real-World Analogy

Imagine driving a modern car.

The **engine** determines how powerful the car is.

The **driver** decides where the car should go.

The **driving mode** determines how the engine behaves.

```text
                    Car

                     │

        ┌────────────┼─────────────┐

        │            │             │

     Engine       Driver      Driving Mode
```

Mapping this to AI:

```text
                  AI System

                     │

        ┌────────────┼─────────────┐

        │            │             │

      Model        Prompt      Parameters
```

The engine remains the same.

Changing from **Eco Mode** to **Sport Mode** doesn't replace the engine.

Similarly,

changing the temperature from **0.2** to **0.9** doesn't create a different model.

It simply changes how that model behaves.

---

# Where Are Parameters Used?

Many beginners assume that an API request only contains the user's prompt.

In reality, a request contains much more information.

Conceptually, it looks like this.

```text
User Prompt

+

Temperature

+

Max Tokens

+

Stop Sequences

↓

Language Model

↓

Generated Response
```

Every token generated by the model is influenced by these settings.

This is why two identical prompts can produce different outputs if the configuration changes.

---

# LangChain and Configuration Parameters

One of LangChain's major design goals is to provide a unified interface across model providers.

For example, with OpenAI:

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="gpt-4.1",
    temperature=0.2,
    max_tokens=500
)
```

Now consider Anthropic.

```python
from langchain_anthropic import ChatAnthropic

llm = ChatAnthropic(
    model="claude-3-sonnet",
    temperature=0.2,
    max_tokens=500
)
```

Although the provider changes,

the overall configuration pattern remains almost identical.

This consistency is one of the reasons LangChain simplifies working with multiple providers.

---

# The Generation Pipeline

Understanding where parameters are applied helps clarify their purpose.

```text
                User Prompt
                      │
                      ▼
             Prompt Processing
                      │
                      ▼
           Apply Configuration
        (Temperature, Max Tokens,
         Stop Sequences, etc.)
                      │
                      ▼
              Language Model
                      │
          Predict Next Token
                      │
                      ▼
          Predict Next Token
                      │
                      ▼
          Predict Next Token
                      │
                      ▼
             Final Response
```

Notice that the parameters are applied **during inference**, not during training.

They influence how each token is selected.

---

# The Most Important Parameter — Temperature

Whenever developers discuss LLM configuration,

the first parameter they usually mention is **Temperature**.

Temperature controls the **randomness** of token selection.

A lower temperature makes the model more deterministic.

A higher temperature makes the model more creative.

Importantly,

temperature does **not** make a model smarter.

It only changes how the model chooses among likely next tokens.

---

# Understanding Temperature Through Probability

Suppose the model receives this prompt.

```text
The capital of France is
```

Internally,

the model predicts several possible next tokens.

| Token  | Probability |
| ------ | ----------: |
| Paris  |         98% |
| Lyon   |          1% |
| London |         <1% |
| Berlin |         <1% |

With a temperature close to **0**,

the model almost always selects the highest-probability token.

Result:

```text
Paris
```

Now consider a different prompt.

```text
Suggest a fantasy kingdom name.
```

Possible predictions:

| Token    | Probability |
| -------- | ----------: |
| Eldoria  |         25% |
| Valoria  |         22% |
| Arcanis  |         18% |
| Drakmoor |         15% |
| Solareth |         12% |

With a higher temperature,

the model explores more of these alternatives,

leading to more varied outputs.

Imagine a teacher asks every student:

> "Name a fruit."

### Student A

Always answers:

```
Apple
```

Every single time.

Very predictable.

Very consistent.

---

### Student B

Answers:

* Mango

* Pomegranate

Different answer each time.

More creative.

Temperature determines where the language model sits between these two extremes.

---

# Temperature Scale

Although the exact implementation varies slightly across providers,

the intuition remains consistent.

| Temperature | Typical Behavior     |
| ----------- | -------------------- |
| **0.0**     | Almost deterministic |
| **0.2**     | Very consistent      |
| **0.5**     | Balanced             |
| **0.7**     | Creative             |
| **1.0**     | Highly diverse       |

Some providers support values greater than **1.0**, but higher values often produce increasingly unpredictable outputs.

---

# Choosing the Right Temperature

There is no universally correct value.

It depends entirely on the application.

### Low Temperature (0.0 – 0.3)

Best suited for:

* Code generation
* SQL generation
* Data extraction
* JSON generation
* Contract analysis
* Medical documentation
* Mathematical reasoning

The goal is consistency.

---

### Medium Temperature (0.4 – 0.7)

Useful for:

* General chatbots
* Customer support
* Educational assistants
* Knowledge retrieval

This range balances creativity with reliability.

---

### High Temperature (0.8 – 1.0)

Appropriate for:

* Story writing
* Marketing content
* Brainstorming
* Poetry
* Character creation
* Game dialogue

These applications benefit from diverse responses.

---

# Common Misconception

One of the most common beginner myths is:

> "Higher temperature means the model is thinking harder."

It isn't.

The model's knowledge does not change.

Its reasoning capability does not change.

Only the randomness in token selection changes.

A higher temperature may produce more original responses,

but it may also increase inconsistency.

---

# Max Tokens

Another essential configuration parameter is **Max Tokens**.

This parameter specifies the **maximum number of output tokens** the model is allowed to generate.

Think of it as a safety limit.

---

# Why Does Max Tokens Exist?

Imagine asking:

```
Explain Artificial Intelligence.
```

Without any output limit,

the model might generate thousands of tokens.

Long responses increase:

* latency
* API cost
* response time
* unnecessary verbosity

Max Tokens allows developers to control these trade-offs.

---

# Example

```python
llm = ChatOpenAI(
    model="gpt-4.1",
    max_tokens=300
)
```

This does **not** force the model to generate 300 tokens.

Instead,

it means:

> "Generate **up to** 300 tokens."

If the answer naturally ends after 120 tokens,

generation stops.

If the model reaches 300 tokens before completing,

the response is truncated.

---

# Input Tokens vs Output Tokens

Developers often confuse these two concepts.

```text
User Prompt

↓

800 Input Tokens

↓

Language Model

↓

200 Output Tokens
```

Input tokens include:

* system prompt
* user messages
* conversation history
* retrieved documents
* tool outputs

Output tokens are the model's generated response.

Both typically contribute to billing and context usage.

---

# Common Beginner Mistake

Many developers assume:

> "Max Tokens controls the total request size."

It doesn't.

It controls **only the maximum generated output**.

The total context also includes the input tokens.

---

# Stop Sequences

Sometimes you don't want the model to decide when generation should stop.

Instead,

you want your application to control it.

This is the purpose of **Stop Sequences**.

A stop sequence is a predefined string that instructs the model:

> "Stop generating when this sequence appears."

---

# Example

Suppose your prompt template looks like this.

```text
Question:
What is LangChain?

Answer:
```

You configure the following stop sequence:

```text
Question:
```

If the model starts generating another question,

generation stops automatically before that sequence.

---

# Where Are Stop Sequences Used?

Although modern chat-based APIs rely less on explicit stop sequences than older completion models,

they are still useful for:

* Prompt templates
* Multi-step workflows
* Legacy completion APIs
* Controlled text generation
* Preventing unnecessary continuation

Understanding stop sequences remains valuable because many providers continue to support them.

---

# Putting Everything Together

A complete generation request conceptually follows this flow.

```text
                User Prompt
                      │
                      ▼
          Configuration Parameters
      ┌─────────────────────────────┐
      │ Temperature                 │
      │ Max Tokens                  │
      │ Stop Sequences              │
      └─────────────────────────────┘
                      │
                      ▼
              Language Model
                      │
          Token-by-Token Generation
                      │
                      ▼
              Final Response
```

Notice that the **model itself never changes**.

Only the generation process changes.

# Production Best Practices

Different applications require different parameter settings.

| Application           | Recommended Temperature |
| --------------------- | ----------------------: |
| Code Generation       |               0.0 – 0.2 |
| SQL Generation        |                     0.0 |
| Data Extraction       |                     0.0 |
| Customer Support      |               0.2 – 0.4 |
| Educational Assistant |               0.3 – 0.6 |
| Creative Writing      |               0.8 – 1.0 |
| Brainstorming         |               0.8 – 1.0 |

These are starting points.

Production teams usually evaluate multiple settings before deciding on the best configuration.

---

# Common Beginner Mistakes

### Setting Temperature Too High

High temperatures can produce inconsistent factual answers.

---

### Using Very Low Temperature for Creative Tasks

Creative applications may become repetitive and predictable.

---

### Setting Max Tokens Too Low

Responses may be cut off before completion.

---

### Setting Max Tokens Excessively High

Higher limits can increase cost and latency, even if the model does not use the full allowance.

---

### Ignoring Application Requirements

The same parameter values rarely work well across all use cases.

Always tune parameters based on the specific application rather than using a single configuration everywhere.

# Key Takeaways

* Model configuration parameters influence **how** an LLM generates text during inference.
* The **model**, **prompt**, and **configuration parameters** are distinct concepts with different roles.
* **Temperature** controls randomness and creativity, while **Max Tokens** limits the maximum response length.
* **Stop Sequences** allow applications to terminate generation at predefined points.
* Effective parameter tuning depends on the application's goals, such as consistency for coding assistants or creativity for storytelling.
